description: "Set connection, request and concurrency limits for the network listeners, IMAP, JMAP, HTTP and WebDAV."

A server has finite resources, and connection and request limits decide how much of them any one client can hold. They bound open sockets per listener, sessions and parallel requests per account, and requests per minute. Setting them is a balance between two failures. A limit that is too low for legitimate use shows up as refused connections or throttling errors. A limit that is too high lets a single client, or a misbehaving one, occupy resources meant for everybody.

This page describes the limits in the order in which they are most often reached. Each protocol's settings page lists the remaining fields.

## Listener connection limits

The first limit a client meets is the one on the listener it connects to. Each [NetworkListener](/docs/ref/object/network-listener) (found in the WebUI under <!-- breadcrumb:NetworkListener --><svg class="lucide-icon" width="1em" height="1em" xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" ><path d="M10 5H3" /><path d="M12 19H3" /><path d="M14 3v4" /><path d="M16 17v4" /><path d="M21 12h-9" /><path d="M21 19h-5" /><path d="M21 5h-7" /><path d="M8 10v4" /><path d="M8 12H3" /></svg> Settings › <svg class="lucide-icon" width="1em" height="1em" xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" ><path d="M17 19a1 1 0 0 1-1-1v-2a2 2 0 0 1 2-2h2a2 2 0 0 1 2 2v2a1 1 0 0 1-1 1z" /><path d="M17 21v-2" /><path d="M19 14V6.5a1 1 0 0 0-7 0v11a1 1 0 0 1-7 0V10" /><path d="M21 21v-2" /><path d="M3 5V3" /><path d="M4 10a2 2 0 0 1-2-2V6a1 1 0 0 1 1-1h4a1 1 0 0 1 1 1v2a2 2 0 0 1-2 2z" /><path d="M7 5V3" /></svg> Network › Listeners<!-- /breadcrumb:NetworkListener -->) accepts at most [`maxConnections`](/docs/ref/object/network-listener#maxconnections) connections at the same time, shared by all its bind addresses.

A listener without its own value uses [`maxConnections`](/docs/ref/object/system-settings#maxconnections) on [SystemSettings](/docs/ref/object/system-settings), which is <!-- default:SystemSettings.maxConnections -->8192<!-- /default --> unless changed. That value applies to each listener separately and is not a total for the server. Five listeners without their own limit can therefore together hold five times as many connections.

Before the server accepts a new connection, the operating system queues it for the listener, and [`socketBacklog`](/docs/ref/object/network-listener#socketbacklog) sets the length of that queue. A larger backlog absorbs bursts of new connections, such as many clients reconnecting after a network outage.

When a listener is at its limit, new connections are refused, and the `limit.concurrent-connection` counter and event increase. Both settings take effect after a restart, as described in [Listeners](/docs/server/listener).

The operating system imposes a limit of its own that must be planned with these. Every connection holds an open file, so the operating system's limit on open files must cover the sum of all listener limits plus the files the server opens itself. The systemd unit installed by the installation script sets `LimitNOFILE=65536`.

## Per-account limits for IMAP, POP3 and ManageSieve

A listener limit protects the server as a whole; the per-account limits keep one account from taking more than its share. On the [Imap](/docs/ref/object/imap) object (found in the WebUI under <!-- breadcrumb:Imap --><svg class="lucide-icon" width="1em" height="1em" xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" ><path d="M10 5H3" /><path d="M12 19H3" /><path d="M14 3v4" /><path d="M16 17v4" /><path d="M21 12h-9" /><path d="M21 19h-5" /><path d="M21 5h-7" /><path d="M8 10v4" /><path d="M8 12H3" /></svg> Settings › <svg class="lucide-icon" width="1em" height="1em" xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" ><path d="M17 19a1 1 0 0 1-1-1v-2a2 2 0 0 1 2-2h2a2 2 0 0 1 2 2v2a1 1 0 0 1-1 1z" /><path d="M17 21v-2" /><path d="M19 14V6.5a1 1 0 0 0-7 0v11a1 1 0 0 1-7 0V10" /><path d="M21 21v-2" /><path d="M3 5V3" /><path d="M4 10a2 2 0 0 1-2-2V6a1 1 0 0 1 1-1h4a1 1 0 0 1 1 1v2a2 2 0 0 1-2 2z" /><path d="M7 5V3" /></svg> Network › IMAP<!-- /breadcrumb:Imap -->), [`maxConcurrentConnections`](/docs/ref/object/imap#maxconcurrentconnections) limits the authenticated sessions of one account to <!-- default:Imap.maxConcurrentConnections -->16<!-- /default --> unless changed. The limit counts IMAP, POP3 and ManageSieve sessions together.

A login beyond the limit is refused, as described in [Concurrent sessions](/docs/email/settings/ratelimit#concurrent-sessions), and the `limit.concurrent-request` event is emitted at the `debug` level. Legitimate use can reach this limit: some clients open one connection per folder, and a user with several devices opens sessions from each of them. Raise the limit to what those accounts need, but not to the point where one account can hold hundreds of sessions.

The second per-account limit is on the rate of commands. [`rateLimit`](/docs/ref/object/imap#ratelimit) limits the commands one account may issue per period, and it applies to IMAP, POP3 and ManageSieve. A client over the limit receives a temporary error, and the `limit.too-many-requests` counter increases. Accounts that hold the `unlimitedRequests` permission are exempt from the rate limit, but not from the session limit.

Both settings take effect after a settings reload, with one exception. `maxConcurrentConnections` is applied to an account when its session data is loaded into the access token cache. An account that is already cached therefore keeps the previous session limit until its entry is evicted, or until all caches are cleared with the `InvalidateCaches` action:

```sh
stalwart-cli create Action/InvalidateCaches
```

Very large mailboxes need a different kind of protection, because a single command on them can be expensive. The settings that provide it, [`maxMessagesPerCommand`](/docs/ref/object/imap#maxmessagespercommand), [`minUidBatchSize`](/docs/ref/object/imap#minuidbatchsize) and [`maxUidBatches`](/docs/ref/object/imap#maxuidbatches), are described in [IMAP settings](/docs/email/settings/imap).

## WebDAV and calendar limits

WebDAV requests can ask for large amounts of data at once, so their limits bound the size of a single request rather than the number of requests. ## Worker threads

The threads that run network and protocol work have no registry setting. The server starts one per CPU core, and only the `TOKIO_WORKER_THREADS` environment variable changes the number. The RocksDB and SQLite data stores run a separate pool, which is sized by their `poolWorkers` setting. Both pools are described in [Worker threads](/docs/server/general#worker-threads).
